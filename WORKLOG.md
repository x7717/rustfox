## Iteration 2 — v0.2 ancestor Bloom filter (bloom gate)

**Гипотеза:** как в Stylo — фильтр предков (2048 бит, fibonacci hashing) позволяет
пропускать весь обход цепочки предков, если нужный тег/класс заведомо отсутствует.

**Результат: РЕГРЕССИЯ ~2%.** Честно фиксируем:

| bench | time | Δ vs naive |
|---|---|---|
| style_pass/optimized/2000 | 2.5225 ms | **+5%** |
| style_pass/optimized/10000 | 12.829 ms | **+4.5%** |

**Разбор:** в фикстуре всего 8 тегов + 64 класса = 72 разных id на 2048 бит (~3.5%
заполнение), а деревья глубокие (depth 12) — почти любой compound «возможно»
присутствует среди предков, gate почти не отсеивает, но каждый probe стоит тактов.
Вывод: bloom-фильтр в Stylo работает на реальных таблицах стилей с избирательными
селекторами; на нашем синтетическом профиле он не является узким местом. Оставлен
в коде (он защищает descendant-обходы), но главный выигрыш искал дальше.

## Iteration 3 — v0.3 subject bucketing (rule hash)

**Анализ:** доминирующая стоимость наивного прохода — 10k узлов × 200 селекторов =
2M проверок subject-compound, из которых подавляющее большинство мгновенно
проваливается (тег/класс не те). Это то же место, где настоящий Stylo применяет
rule hash: селекторы раскладываются по бакетам правого (subject) compound.

**Реализация:** `StyleSet::new` строит бакеты по ключу `(subject_tag, subject_first_class)`;
узел проверяет только кандидатов из своих бакетов (≤ ~15 вместо 200), затем
subject-классы перепроверяются локально, и только потом запускается обход предков
с bloom-gate.

| bench | time | Δ vs naive |
|---|---|---|
| style_pass/indexed/2000 | 762.95 µs | **3.15x** |
| style_pass/indexed/10000 | 4.0901 ms | **3.0x** |

## Iteration 4 — v0.4 zero-alloc flat output + микрооптимизации

**Изменения:**
1. Выход `MatchedStyles { starts, ends, indices }` вместо `Vec<Vec<u32>>` —
   минус 10k аллокаций на проход (одна Vec на узел исчезла).
2. Убран временный Vec классов узла — итерация по `n.classes` на месте.
3. Парити-багфиксы по пути:
   - `ends[node]` писался после обхода поддерева → диапазон корня захватывал матчи
     потомков (поймано parity-тестом, узел 0);
   - fixture мог выдать узлу дублирующийся класс (`c17 c17`) → бакет посещался
     дважды → дубликат в выдаче (поймано parity-тестом, узел 194). Класс-лист —
     множество: дедупликация в генераторе.

| bench | time | Δ vs naive | Δ vs v0.3 |
|---|---|---|---|
| style_pass/indexed/2000 | **437.98 µs** | **5.26x** | −42.6% |
| style_pass/indexed/10000 | **2.6482 ms** | **4.45x** | −35.3% |

Итог четырёх итераций: **4.4–5.3x** к наивной базе при байт-в-байт равных результатах
(parity-тесты на 3 фикстурах + синтетические селекторы с изоляцией bloom-семантики).

   - SIMD-сравнение классов (AVX2) для compound с 2+ классами.
5. Обновить `bench/latest.json` и дописать новую итерацию сюда.

## Iteration 5 — v0.5 walk-based rebuild → v0.6 bit-parallel automaton

**Исходная точка (v0.4):** indexed matcher, 437.98 µs @ 2k / 2.6482 ms @ 10k.

### v0.5 — точечные оптимизации поверх архитектуры v0.4

Замеры профилировщика фаз (10k фикстура) показали на v0.4:
heap-аллокацию `Frame` в bloom на **каждый узел**, 4+ хеш-пробы бакетов
на узел, линейный `Vec::contains` по классам, разбросанную память DOM.

1. **Direct-index dispatch** — `FxHashMap<(Option<u32>, Option<u32>), _>` →
   вложенные `Vec` по плотным id: 4+ проб на узел → индексация массивом.
2. **u128-битмаски классов** — членство класса в compound: линейный поиск →
   один AND (id < 128; старшие — в spill-списке, модель общая).
3. **SoA-флаттенинг DOM** — теги/маски/дети в непрерывные массивы.
4. **Undo-log bloom** — `Frame { Vec }` (аллокация на узел) → общий лог
   `(word, old)` с откатом к метке: кадр DFS = 12 байт.
5. **Итеративный DFS** вместо рекурсии.

Промежуточный итог: **348 µs @ 2k / 2.02 ms @ 10k** (1.26x / 1.31x к v0.4).

### v0.6 — смена архитектуры: бит-параллельный автомат

Профиль v0.5 упёрся в фундамент архитектуры «справа-налево»: каждый
кандидат ⇒ обход цепочки предков, стоимость `кандидаты × глубина`.
Архитектура переписана на top-down бит-параллельный NFA (приём
бит-параллельных regex-движков, поднятый на деревья):

- каждый `(селектор i, compound j)` = бит в банке `u128`-слов;
- `act[u]` — префиксы, заканчивающиеся точно в узле u; `acc[u]` — объединение
  `act` по пути корень→u;
- переход на узле за O(W) слов: Child-пары берут `act[parent] << 1`,
  Desc-пары — `acc[parent] << 1`, всё AND `ok[u]`;
- `ok[u]`: пары без классов — прямым индексом по тегу (без пробы), остальные —
  по точной маске классов (маска compound обязана быть подмножеством маски
  узла ⇒ `2^popcount-1` проб);
- выдача идёт по возрастанию селекторов прямо из битсета — сортировка не нужна;
- bloom-фильтр и обходы предков удалены полностью.

**Честные регрессии по пути (зафиксированы и отброшены):**
- кэш `(tag, mask) → ok` — **+23% @ 10k**: промахи (хеш + вставка + копия
  строки) дороже 3.7 средних проб; в фикстуре слишком много различных масок;
- плотная упаковка пар (Σlen вместо K·n, W 5→4) + extraction через
  префиксные суммы — **+25% @ 10k**; K-паддинг с делением на константу
  (mul-shift) оказался быстрее бинарного поиска по границам.

**Итог (criterion, стабильные прогоны):**

| bench | naive | v0.4 indexed | v0.6 fast | Δ vs naive | Δ vs v0.4 |
|---|---|---|---|---|---|
| style_pass/2000 | 2.330 ms | 446.1 µs | **310.5 µs** | **7.5x** | 1.44x |
| style_pass/10000 | 11.805 ms | 2.493 ms | **1.742 ms** | **6.8x** | 1.43x |

Парити: побайтовое равенство с naive на фикстурах (включая классы с
произвольными id — spill-путь покрыт тестом `fast_handles_high_class_ids`).

## Iteration 6 — v0.7 (автомат + AVX2) и четыре новых горячих ядра

**Исходная точка (v0.6):** 310.5 µs @ 2k / 1.742 ms @ 10k (7.5x/6.8x к naive).

### A. Style-движок v0.7

Профиль v0.6: на каждый узел — memcpy 2×wr×16B parent-стейта в scratch + скалярный
переход по W u128-словам + per-node `Vec` hi-классов в SoA.

1. **Zero-copy parent reads** — v0.6 копировал `pact/pacc` из `level_store`
   в scratch; v0.7 читает срезы прямо из стора. Минус 2×wr×16B memcpy на узел.
2. **AVX2-переход** — `act = ok & ((child & act_sh) | (desc & acc_sh) | first)`
   и `accn = pacc | act` — чистые битовые операции: 2 u128-слова (32B) за
   инструкцию, детекция один раз на проход. Банки выровнены до чётного `wr`.
3. **SoA hi-классы CSR** — `Vec<Vec<u32>>` → `hi_start/hi_list`, ноль per-node Vec.
4. **Direct-mapped ok-cache** (`style_pass_cached`) — фикс. таблица 2048 слотов
   с фингерпринтом (tag, mask) и inline `[u128; 8]` пейлоадом. **Честный
   регрессионный результат:** −4% на фикстуре (повторяемость (tag, mask) ≈30%
   мала; хит = копия 128B vs ~4 хеш-пробы). Метод оставлен публичным: в реальных
   словарях классов повторы гораздо плотнее. Оба варианта в bench.

**Регрессия, найденная и отброшенная:** BFS (level-order) банки — родители
читаются последовательно из банка уровня L−1, дети стримятся в уровень L.
Красиво на бумаге, но рабочий сет становится **O(ширина уровня) ≈ 600KB**
(L2/L3-трафик) вместо O(глубина) ≈ сотни байт в L1 у DFS → **+32% @ 10k**.
Откат на DFS; выигрыши (zero-copy, AVX2, cache, CSR) от порядка обхода
не зависят и сохранены.

**Итог (criterion, стабильные прогоны):**

| bench | naive | v0.6 | **v0.7** | Δ vs naive | Δ vs v0.6 |
|---|---|---|---|---|---|
| style_pass/2000 | 2.3025 ms | 310.5 µs | **289.12 µs** | **7.96x** | 1.07x |
| style_pass/10000 | 12.000 ms | 1.742 ms | **1.5958 ms** | **7.52x** | 1.09x |

Парити: побайтовое равенство с naive (включая новый `style_pass_cached` и
spill-путь классов ≥128).

## Iteration 7 — v0.8: инкрементальный restyle + однопроходный URL-битмап + fused-токенизатор

Дата: 2026-10-23. Три фронта параллельно (2 субагента + ядро style в главной сессии).

### A. rustfox-style v0.8 — ИНКРЕМЕНТАЛЬНЫЙ RESTYLE (архитектурное добавление)

**Идея.** Датафлоу автомата строго parent → child (`act`/`acc` узла зависят
только от состояния родителя и собственного `(tag, class-mask)`) → изменение
класса узла `u` может повлиять ТОЛЬКО на поддерево `u`. Это ровно инвариант,
на котором стоит incremental restyle в Stylo.

**Механика (v0.8):**
- `SoaCache` получил `parent[]` + DFS `preorder[]` (корни по возрастанию,
  дети по возрастанию — байт-в-байт порядок `style_pass`); поддерево любого
  узла — НЕПРЕРЫВНЫЙ диапазон `[pre_start[u], subtree_end[u])` (размеры —
  обратным накоплением по preorder, O(n));
- `StateStore` — персистентные состояния всех узлов (`act`/`accn`,
  2·n·wr·16B ≈ 2.5 MB @ 10k×200 селекторов) — «style data на элементе»;
- `restyle(soa, states, prev, dirty)`: флаги dirty → расширение до
  замыкания по поддеревьям (один линейный проход по preorder, родитель
  всегда раньше ребёнка) → линейная перестройка арены: чистые узлы копируют
  свой прежний диапазон индексов (memcpy), dirty-поддеревья прогоняют
  автомат по непрерывному срезу, freshly-written parent states читаются
  прямо из store. Ни стека, ни рекурсии;
- `style_pass_states` — полный проход с записью состояний (preorder-цикл
  вместо DFS-стека) — база для цепочки restyle'ов;
- `SoaCache::set_class(u, class, on)` — инкрементальное обновление классов:
  O(1) для id < 128, O(n) CSR-rebuild для hi-классов (редкий путь).

**Парити (жёстче, чем у прошлых итераций):**
- 25 рандомизированных раунов dirty-множеств (1..=80 узлов, оконные + глобальные
  выборки, чейнинг prev/state между раундами): matched sets И StateStore биты
  бит-в-байт равны свежему полному проходу;
- end-to-end против naive-матчера по сырому DOM (8 раундов);
- hi-class spill (c130/c200 toggle), dirty-корень (пересчёт всего дерева),
  вложенные dirty в одном поддереве, дубликаты и out-of-range id,
  экстремумы all/none.

**Числа @ 10k (criterion, full recalc = 1.586 ms):**

| dirty | restyle | Δ vs full |
|---|---|---|
| 0.1% (10 узлов) | 168.4 µs | **9.4x** |
| 1% (100) | 218.2 µs | **7.3x** |
| 5% (500) | 577.1 µs | **2.7x** |
| 10% (1000) | 1.028 ms | 1.5x |
| 25% (2500) | 1.649 ms | 0.96x (кроссовер) |

Физика кроссовера честно: при 25% рассыпанных dirty закрывается большая
часть поддеревьев (сумма ≈ полный проход) + O(n) пол перестройки арены
(~160 µs при 0.1% — там он и виден как floor).

Попутно исправлена дока v0.7: BFS bank-раскладка была ОТКАЧЕНА ещё в
Iteration 6 (+32%), заголовок модуля вводил в заблуждение; теперь история
зафиксирована корректно (preorder — это порядок итерации, не раскладка
памяти, аргумент про working set на него не действует).

### B. rustfox-url — ОДНОПРОХОДНЫЙ БИТМАП-ДВИЖОК (1.15x → 1.68x)

Один AVX2/SSE2-проход классифицирует структурные байты
(`:` `/` `?` `#` `@` `[` `]`): на 32-байтный чанк 7 сравнений + 7 movemask,
OR в одну u32-маску чанка. Все компоненты выводятся из упорядоченного
потока масок через trailing_zeros — буфер проходится РОВНО ОДИН раз вместо
3–5 сканов v0.7. Гибридный диспатч по длине (пороги измерены diag-примером,
после — удалён): скаляр вне BITMAP_MIN_LEN..=2 KiB.

| движок | время | vs naive |
|---|---|---|
| **bitmap (= parse)** | **102.5 µs** | **1.68x** |
| scans (v0.7, сохранён как parse_scans) | 143.3 µs | 1.20x |
| naive | 171.9 µs | 1.00x |

Парити: все 2000 фикстурных URL — все компоненты bitmap ≡ scans; LCG-случайные
строки; префиксы/паддинги; ручные углы. 15/15 тестов крейта.

### C. rustfox-html — FUSED-ТОКЕНИЗАТОР (плоская арена событий)

Второй API рядом с pull: `tokenize_into(src, &mut TokenBuf)` — ОДИН слитный
цикл по буферу без per-token вызовов; события — плоский POD `Event`
(20 байт, 4-byte aligned), атрибуты — параллельная арена `RawAttr`.
Внутри: 256-байтовая LUT классов байта, SWAR-проба 16B перед find_byte,
find_sub_arrow для `-->`.

| режим | fused | pull | naive |

## Iteration 8 — v0.9: streaming html (`for_each_event`, без арены) + http1 two-pass

### A. rustfox-html — колбэк-контракт одного прохода

Arena-налог убран не тюнингом, а сменой контракта. Ядро fused-цикла вынесено в
крейт-приватный `tokenize_core<S: Sink>` (мономорфизация при компиляции, без
рантайм-диспатча):

| sink | публичный API | что делает |
|---|---|---|
| `ArenaSink` | `tokenize_into` | как раньше: Event/RawAttr в два плоских Vec (кодген прежний) |
| `CallbackSink` | **новый `for_each_event(src, \|kind,a,b,attrs\| …)`** | событие отдаётся потребителю в момент скана, атрибуты тега — срезом скретча; арены нет вообще, второго прохода нет |

`tokenize_into` стал тонкой обёрткой над тем же ядром → один сканер на три API
(pull / arena / streaming). Парити-оракул расширен до трёхстороннего
**pull ≡ arena ≡ callback** — все прежние тесты (35 hand-фикстур, 14 truncated,
LCG 8×2000, изолированные piece-kind'ы, dense/prose страницы) автоматически
гоняют и колбэк-путь.

| режим | callback | fused | pull | naive | callback vs naive |
|---|---|---|---|---|---|
| prose | **88.0 µs** | 98.3 µs | 99.5 µs | 178.4 µs | **2.03x** (лучший результат проекта) |
| dense | **383.8 µs** | 405–438 µs | 437.1 µs | 281.9 µs | 0.73x (см. физику) |

Честная dense-физика: callback быстрее fused на 1.06–1.14x и pull на 1.14x —
налог materialize+второй-проход исчез (383.8 µs = лучшее rustfox-время на dense
за весь проект, было 409.9); остаток до naive — сам сканер на ранах 1–15B +
диспатч колбэка на событие (scan-only floor 329 µs из diag Iteration 7).
Оговорка о машине: naive на сегодняшнем тихом прогоне 281.9 µs — на 16% быстрее
своей же истории v0.8 (335.3), поэтому «vs naive» ухудшилось при улучшении
абсолютного времени; оба числа зафиксированы. Публичный контракт колбэка:
`kind` (бит self-closing как в `Event`), диапазон `a..b` исходника, срез
`&[RawAttr]` атрибутов этого тега — валиден только внутри вызова.

### B. rustfox-http1 — two-pass с записью концов строк

38/39/45 заголовках). Pass 2 потребляет записанные офсеты вместо повторных

одним 4-байтовым сравнением вместо трёх соседних загрузок. Публичный API не
изменился.
